# 에이전트 역할 분담과 Git 체크포인트 운영

이 절차는 Windows 데스크톱의 에이전트 작업을 대상으로 한다. 부모 세션이 작업 범위, 결과 채택, 통합과 검증을 맡는다. 공개 저장소에는 공개 범위를 확인한 산출물만 옮긴다.

| 역할 | 책임 |
| --- | --- |
| 부모 세션 | 작업 범위와 파일 소유자를 정하고, 두 SOL 검수 결과와 통합 테스트를 확인한 뒤 커밋 담당자 한 명을 지정한다. |
| Devin 작업자 | 서로 겹치지 않는 범위에서 후보 변경과 검증 근거를 반환한다. 동시 실행은 최대 10개까지 수용할 수 있으며, 실제 배정은 독립 작업 수와 자원 여유에 맞춘다. |
| SOL 1 — 동작 검수 | 후보의 동작, 변경 범위와 회귀 가능성을 점검하고, 후보와 동일한 버전에 묶인 테스트 결과를 확인한다. |
| SOL 2 — 공개 범위 검수 | 공개 기준본과 후보를 대조해 로컬 변경, 다른 작업자의 변경, 비공개 데이터가 섞이지 않았는지 확인한다. 기준본 및 변경 전 지문과 복구 절차도 검수한다. |

1. **작업을 등록하고 두 기준을 따로 기록한다.** `scripts/work_journal.py`의 `open`에 작업 ID, 담당자, 허용 상대 경로를 기록한다. 공개 원격 기준본의 커밋 SHA와 대상 파일 지문 또는 부재 상태를 기록한다. 별도로 로컬 `HEAD`, 대상 파일의 실제 변경 전 지문 또는 부재 상태, 대상의 스테이징 상태와 복구 참조를 기록한다. 같은 경로라도 두 기준은 각각 보존한다. 공개 기준본은 공개 후보를 만드는 출발점이고, 로컬 변경 전 상태는 작업 보존과 복구에 쓴다.
2. **범위를 나누고 독립 후보를 받는다.** 작업자마다 겹치지 않는 허용 경로를 배정한다. Windows 관리 대기열의 작업자 상한 10개를 사용하고, CPU·메모리와 파일 충돌 검사 결과에 따라 실제 시작 건수를 줄인다. 범위가 지정된 쓰기 브리프에는 단독 줄에 `VERIFY: <실행 명령>`을 적는다. 공통 조상이 확인되지 않으면 공개 검토를 마친 변경을 검증된 공개 기준 커밋 위에 재구성한다. 작업의 상태 변화와 축약한 검증 근거는 `work_journal`의 `note`로 남긴다.
3. **체크포인트에서 재개 근거를 묶는다.** 기존 `scripts/codex_work_checkpoint.py`에서 확인한 내용과 함께 작업 ID, 소유 범위, 두 기준의 참조, 후보 지문, 확인한 검증과 미실행 항목, 남은 판정 및 다음 확인 한 가지를 인계한다. 재개할 때 저장소 루트, 현재 `HEAD`, 해당 파일 소유권과 작업 전 지문을 다시 확인한다. 기준이 바뀌었거나 소유권이 겹치면 해당 후보의 적용을 보류하고 다시 대조한다.
4. **같은 후보를 이중 검수한 뒤 부모가 채택한다.** 두 SOL 역할이 같은 후보 지문에 대해 각각 판정한다. 부모는 승인된 상대 경로 목록, 두 검수 결과와 통합 테스트를 대조한다. 후보가 달라지면 관련 검수와 테스트를 다시 실행한다. 검수 불일치나 필수 근거 누락이 있으면 해당 후보는 보류하고 사유와 다음 확인을 기록한다.
5. **커밋은 한 번에 하나씩 진행한다.** `scripts/git_commit_window.py`의 커밋 창과 잠금 상태를 확인한다. 후보 분류는 검토 자료다. 커밋 담당자 한 명이 승인된 경로만 지정해 `scripts/agent_git_vibe_commit.py`의 `--dry-run`으로 계획을 확인한다. 실제 실행에 사용하는 격리 인덱스에서 스캔 결과를 확인한다. 실행 직전에 기준, 소유권, 후보 지문, 잠금을 다시 확인하고, 충돌 시 기다린다. 다른 세션의 잠금과 스테이징은 보존한다. 커밋 뒤에는 반환된 SHA, 부모와 포함 경로를 대조한다. 커밋 보류 응답을 받으면 재시도 전에 실제 `HEAD`부터 확인한다. 공개 게시가 요청된 경우 GitHub 커넥터로 대상과 공개 범위를 확인한 뒤 전용 브랜치에 기록하고, 읽기 결과를 게시 응답과 대조한다.
6. **실제 실행과 채택을 집계하고 작업을 닫는다.** 작업 ID별 요청, 프로세스 시작, 결과 반환, 부모의 최종 채택을 별개로 센다. 실제 실행 구간에서 최고 동시 실행 수를 계산한다. 동일한 검증 기준을 적용한 작업끼리 채택률, 대기 시간, 검증 완료 시간, 체크포인트 재사용·충돌 건수를 비교한다. 실행 시각이 없으면 미확인으로 남긴다. `work_journal`의 `close`에는 판정과 근거를 남기고, 미완료 항목은 체크포인트에 넘긴다.

## 복구 지점 확인

- 로컬에서 승인된 경로의 변경 전 바이트와 SHA-256을 체크포인트에 보관한다. `codex_work_checkpoint.py restore --run <cycle> --staging <scratch>`로 별도 디렉터리에 복구를 연습하고 파일 지문을 확인한다. 작업 트리 복구 직전에는 현재 파일이 기록된 변경 후 지문과 일치하는지 다시 확인한다.
- Git 섀도 스냅샷의 참조와 커밋은 `agent_git_snapshot.py list --agent <owner> --task-id <task>`로 조회한다. 동일한 `pre` 또는 `post` 단계는 첫 참조를 유지한다. 재시도에서 트리가 같으면 기존 커밋을 사용하고, 달라졌으면 충돌로 기록한다. 새 변경 단위의 스냅샷에는 새 작업 ID를 쓴다.
- 공개 기준 커밋을 보존할 때는 해당 SHA를 가리키는 백업 브랜치를 만들고 커넥터로 다시 읽는다. 새 문서나 코드는 별도 작업 브랜치에 기록해 백업 브랜치의 SHA를 고정한다. 로컬 미커밋 변경은 작업 ID로 보관된 지정 파일별 복구 지점에서 확인한다.

공개 보고에는 저장소 상대 경로, 공개 가능한 지문, 집계와 판정만 넣는다. 로컬 백업 위치와 상세 로그는 접근이 제한된 내부 기록에서만 참조한다. 자격 증명과 비공개 입력은 인계 문서에 남기지 않는다. 새 파일의 변경 전 상태가 부재였다면, 복구할 때 기록된 변경 후 지문이 그대로인 경우에만 그 파일을 제거한다.

커밋 도구의 회귀 확인: `python -X utf8 -B scripts/test_agent_git_vibe_commit.py`. 종료 코드 0을 확인한다. 이 테스트는 임시 저장소에서 커밋 가드를 검증하며, 공개 후보의 통합이나 원격 반영 증거는 별도로 확보한다.
