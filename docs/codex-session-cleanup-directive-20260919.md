## Phase 1 — 기억 유입 차단 (정리 작업보다 먼저)

순서: 현재 설정 기록(Phase 0) → **필요한 범위의 기억 사용·생성 일시 중단** → Phase 2 이후.

1. 공식 문서와 설치 버전 일치를 확인한 뒤, 다음 제어를 **구분해서** 사용한다:
   - `use_memories`: 이후 세션에 **기존 기억을 주입할지** 제어.
   - `generate_memories`: 새 대화를 **기억 생성 입력으로 저장할지** 제어.
   - `/memories`: 지원 클라이언트에서 현재 대화의 기억 사용·생성 기여 조절.
2. `generate_memories=false`만으로는 **기존 세션의 생성 자격과 이미 만들어진 기억이 제거되지 않는다** — 기존 입력·생성 상태는 Phase 2에서 별도 처리.
3. **이 정리 작업 자체의 대화**가 잘못된 내용을 다시 기억시키지 않도록, 지원 클라이언트에서는 `/memories` 등으로 현재 대화의 기여를 제한한다.
4. 전체 기억 기능을 **영구적으로 꺼두는 것으로 끝내지 않는다** — Phase 6에서 선별 재개.

**검증**: 차단이 실제 적용됐는가(설정 재조회 + 새 세션에서 기존 기억 미주입 확인). **중단 조건**: 클라이언트별 제어 미지원·적용 불가 시 해당 범위를 `미해결`로 표시하고 무리하게 진행하지 않는다.

## Phase 2 — 오염 입력·생성물 처리

1. `memories_1.sqlite` 잔존 산출물의 역할을 확인한다: `stage1_outputs` 76행(전부 phase2 선정)이 재생성 입력으로 재사용되는지, `jobs` 큐 상태가 재개 시 자동 처리되는지 — 문서·동작으로 확인, 모르면 `evidence_needed`.
2. 오염 확인된 기존 입력(오래된 세션의 stage1 산출물 등)을 **공식 제공 방식으로만** 제외·정리한다. 안전한 제외 수단이 없으면 그 부분을 `미해결`로 표시하고 강제 진행하지 않는다 — 임의의 DB 초기화 절차를 만들지 않는다.
3. `memories\`를 다시 비우는 것만으로 해결됐다고 보고하지 않는다.
4. 생성 대상 범위 확인: 관측상 stage1 처리는 ~399 스레드(전체 4,643 아님) — **연령·유휴·처리량 제한의 실제 설정값**을 공식 설정으로 확인한다. "수천 개 전체가 현재 생성 대상"이라는 전제부터 검증. 필요 없는 전체 재요약·대량 LLM 호출 금지 — 관련 제한은 공식 설정에 있으므로 별도 시스템을 만들지 않는다.

**검증**: 제외된 입력이 실제로 생성·주입 경로에서 빠졌는가(파일 존재가 아니라 대상 지정 기준). **중단 조건**: 제외 수단 부재 → 해당 범위 `미해결` 기록 후 Phase 3로 진행하되 Phase 6 재개 판정에서 불이익 반영.

## Phase 3 — 세션 후보 정리 (복구 가능한 단계부터)

1. **후보 축소는 메타데이터·읽기 전용 조회로** — 제목·스폰 엣지·턴 수·크기·연령은 탐색 신호일 뿐이다. 필요한 후보만 내용을 확인한다.
2. **중복 판정 기준**: 같은 제목은 탐색용. 실제 중복 여부는 작업 내용·변경 파일·결과·남아 있는 고유 증거로 판단한다. 자식 세션에만 있는 테스트 근거·유일 증거는 보존 대상이다.
3. **앱 기능 우선**: 보관·삭제·기억 제외 기능을 우선 검토하되 세 동작을 동일시하지 않는다. 각 기능의 실제 효과 범위(파일만? DB 행? 기억 입력 자격?)를 확인 전 단정하지 않는다.
4. **수동 격리(앱 기능 불충분 시)**:
   - 관련 저장소의 쓰기가 멈췄는지 확인(앱 종료 또는 쓰기 정지 증거).
   - 필요한 범위의 **일관된 복구본 + 원위치 목록** 확보.
   - 기록 스키마: 원본 경로·대상 경로·식별자(thread_id/uuid)·크기·선정 이유·처리 결과. **실제 이동 직전 파일 변경 여부 재확인**.
   - 소량 시험: 목록 표시·세션 재개·부모/자식 참조·복구 정상 확인 → 통과 후 같은 조건 후보를 묶어 배치. **시험 1건만으로 전체 완료 보고 금지**.
5. **기본안에서 제외**: SQLite 본체·인덱스 직접 수정; WAL 삭제(WAL에는 본체 미반영 커밋 가능); 실행 중 DB 본체만 복사(공식 백업 또는 쓰기 정지된 일관 사본 사용); `VACUUM` 임의 실행(잘못된 기억·끊어진 참조를 고치는 기능이 아님 — 논리 정리와 빈 공간 회수를 구분).
6. **우선 보존**: 최근 7일, `E_manual`(재검토 전), `archived_sessions` 13개, 진행 중 작업, 필요한 부모·자식 참조. **파일 보존과 기억 생성 허용은 별개** — 최근 세션이라도 잘못된 전제가 확인되면 기억 생성 대상에서는 제외한다.
7. **보고 구분**: 같은 C: 드라이브의 `_rescue` 이동은 격리량이지 회수량이 아니다. **격리량·백업 증가량·실제 여유 공간 증가량을 따로 보고**하고, 격리본 영구 삭제는 별도 승인 단계로 남긴다.

**검증**: 배치별 기록 스키마 충족·파일럿 체크리스트 통과·복구본 복원 시험. **중단 조건**: 쓰기 정지 확인 불가, 복구본 미확보, 파일럿에서 참조 손실·재개 실패 발견 → 해당 조건 후보 전체 보류 + 원위치 복구.

## Phase 4 — 캐시·인접 항목 정리 (세션과 분리)

1. `visualizations\`는 통째 삭제 금지 — `.png` 스크린샷·`.ndjson`·evidence-snapshot.md·gradle 소스·browser-proof 결과 등 **실기 증거 혼재 확인됨**. 재생성 가능하고 현재 사용되지 않음이 확인된 **캐시성 하위 경로만**(예: `gradle-user-home-*`의 modules-2 캐시) 대상으로 한다. 열거 오류를 손상·삭제 가능의 증거로 쓰지 않는다.
2. `..codex-global-state.json.tmp-*` 18개: 원자 쓰기 잔여로 보이나 내용 확인 후 판단.
3. `logs_2.sqlite`(208,176행): 보존 정책 확인 후 — 임의 축소·VACUUM 금지.
4. `tmp\`,`cache\` 등 지원 디렉터리: 이번 목적과 직접 관련 없으면 건드리지 않는다.

## Phase 5 — 지침 오염 제거 (최소 수정, 캐시 정리와 분리)

1. **새 파일 남발 대신 실제로 읽히는 지침의 충돌 부분만 최소 수정**한다. Codex는 `AGENTS.override.md` > `AGENTS.md` 등 정해진 탐색 순서가 있으므로, 파일을 수정한 사실만으로 적용됐다고 판단하지 말고 **실제 로딩 경로를 확인**한다(현재 관측: `~\.codex\AGENTS.override.md` 부재 → `AGENTS.md` 적용 중).
2. 반영 원칙(압축):
   - 현재 사용자 요청과 프로젝트 지침을 따르고, 프로젝트 상태는 현재 로컬 파일·빌드·실행 증거로 확인한다. 오래된 Git 기록을 최신 소스나 최신 복구본으로 취급하지 않는다.
   - 과거 보고서·세션·기억은 참고 자료다. 폐기된 전제·미검증 성공 보고·당시 임시 지시를 현재 사실이나 상시 규칙으로 승격하지 않는다.
   - 확정된 결론에는 근거 위치와 확인 날짜를 붙인다. 실패 기록도 실패 조건과 재검증 조건을 함께 남기고, 영구 불가능 판정으로 굳히지 않는다.
3. `_rescue`와 폐기 자료가 **실제 자동 수집·검색 경로에서 제외되는지** 확인한다. "읽지 말라"는 문장 추가만으로 기술적 차단이라 보고하지 않는다. 제외 기능이 없으면 그 한계를 명시하고 대량 재수집을 피하는 대안을 제시한다.
4. Cline 전체 import는 계속 보류 — 설치본의 선별 방식·관리 경로를 직접 확인하고, 필요 작업 선별 또는 **현재 상태+검증된 결론만 담은 짧은 인계문**으로 새 작업 시작을 우선한다.

## Phase 6 — 재개·최종 검증

1. 새 세션에서 기존 기억 미주입 확인 → 필요한 기억부터 **선별 재개**(전체 on 복귀가 기본이 아님).
2. 기억 재생성 경로가 관찰될 때까지 재생성 검증은 미완료다.
3. 완료 판정은 **분리 항목**으로 각각 보고한다:
   - ① 차단 설정 적용 확인
   - ② 파일 정리 확인(격리·복구본·목록 검증)
   - ③ 새 세션의 기억 사용 확인
   - ④ 실제 기억 재생성 확인 — 미관찰 시 **"차단 적용 확인, 재생성 검증 미완료"**로 적고 메모리 오염 해결 완료로 묶지 않는다.

## 필수 반례 검증 (검토 시 포함)

- **최근에 다시 연 오래된 오염 세션**: 이력은 보호하면서 기억 생성에서는 제외할 수 있는가?
- **같은 제목이지만 서로 다른 패치를 수행한 세션**: 중복으로 오분류하지 않는가?
- **자식 세션에만 있는 중요 테스트 근거**: 그 근거와 필요한 부모·자식 참조를 보존하는가?
