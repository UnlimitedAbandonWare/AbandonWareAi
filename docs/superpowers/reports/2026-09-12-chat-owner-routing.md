# Ordinary chat owner routing (B4, local implementation and verification)

The previously approved Conversate integration goal remains active. This is a subordinate ordinary-chat reliability change; it neither persists live assistance nor changes the assist output grace or accepted background-task lifetime.

An opt-in `chat.cluster.enabled=true` path uses existing JDBC and WebClient dependencies. `chat.cluster.instance-id` is an opaque operator-chosen node name. `chat.cluster.peers` is an explicit semicolon-delimited mapping of names to origins. Remote origins require HTTPS; literal loopback HTTP is permitted for isolated tests. There is no URL discovery from requests/DB, automatic redirect, proxy-header trust, external credential forwarding, or transport retry. `chat.cluster.secret` / `CHAT_CLUSTER_SECRET` supplies a minimum 32-byte deployment secret through normal property resolution; it is never written by this task. No deployment secret has been provisioned.

The additive `V20260912_05__chat_run_owners.sql` migration contains session slots and token-addressed owner records only: session ID, opaque run token, instance ID, unique process boot ID, state and lease/replay timestamps. No audio, transcript, card, prompt, model answer, user credential, or subscriber identifier is stored there. The migration is executed only in isolated H2 fixtures during this task. Existing MariaDB configuration is unchanged.

Claiming the shared slot precedes local run installation and inference. All registry callers (initial existing session, late/new-session creation, synchronous chat) pass through that claim. An active claim returns a conflict, an expired or unavailable owner returns an explicit temporary-unavailable result; neither starts a replacement inference. An expired active row is an uncertainty tombstone and is not removed by completed-replay cleanup. No provider execution lookup/idempotency contract is assumed. A future explicit recovery policy is needed to resolve such a tombstone; automatic takeover is deliberately absent.

Active execution leases use the DB clock; the local admission/commit deadline uses a conservative monotonic deadline. Process boot IDs prevent a restarted process with the same configured node name from renewing or completing its predecessor's run. Terminal replay is a separate time interval, initially the existing registry's `chat.resume.ttl-seconds` value. A new run does not overwrite the old token-addressed replay record.

Existing public controller session ACL checks run before registry attach/control/state access. The internal peer endpoint accepts a signed exact `(action, sessionId, runToken, time, nonce)` command only. HMAC signatures are checked in constant time, accepted nonces are bounded and expire, and the receiving node must still be the directory's available owner. The signature does not carry a user cookie, password, or API key. This is authenticated server-to-server forwarding after the public authorization boundary, not a public generation endpoint.

Each relayed viewer subscribes once to the owner's existing interactive Flux. Internal replay bridges remain uncounted. Final viewer transport cancellation follows the same owner-side run cancellation path. ACK, final/recovery ACK, and redacted exact state also reach the owner. Ordinary chat's immediate last-viewer policy remains separate from Conversate's five-second recovery grace.

The current-token pointer and exact-state `current` flag consult the shared slot, including when the local node retains an older terminal replay. Session deletion first marks the shared slot DELETING, then waits for the owner-side cancellation fence before the existing durable deletion proceeds. A new run cannot enter through another node while that fence is held. An unavailable/expired owner prevents deletion from claiming a safe fence. This adds no automatic deletion or recovery operation.

The relay uses separate bounded connection pools: stream connections default to at most 128 per peer (configurable downwards with `chat.cluster.max-relay-streams`) with a 64-entry pending acquisition bound; control connections have a 16-connection limit and 32 pending entries. Pending acquisition is capped at one second. Control requests do not wait behind persistent SSE connections. The component closes only these owned pools on shutdown.

Fresh verification: `b4-regression.log`, exit 0, **169 tests, zero failures/errors/skips**. These include 10 real loopback HTTP/cluster tests and five shared-directory tests, plus the affected registry, initial/disconnect, sync, UTF-8 stream, input/ownership, cancellation and state-security contracts. Earlier 25-test and failed 114-test runs are preserved separately; they are not added to the 169 count. Failures found during this change were stale global current-token selection, missing cross-node deletion fencing, a callback/terminal-transition test race, and an uninitialized replay capacity in a directly constructed test registry. The two test defects were corrected without extending the two-second transport/transition bounds.

The final relay disconnect sample observed the owner cancellation handler after **357 ms, n=1**. Terminal CANCELLED state and internal sink completion were asserted separately. This is not a measured TCP FIN timestamp, provider/GPU stop duration, or p95. The server-shutdown test closes one isolated relay HTTP server and verifies owner cancellation; a hard kill of a separate JVM is still distinct evidence. A one-slot saturated stream pool still allowed ACK/cancel through the independent control pool. DB connection failure refused new work and cancelled the affected local execution. The directory's simultaneous-five-claim, same-name/new-boot, retention, and expired-lease cases passed without takeover.

The two loopback servers are isolated Spring application contexts with a shared synthetic H2 DB. They are not production MariaDB/Redis/load-balancer proof or two independent machine/process failure proof. No real GPU/provider stop, phone capture, glasses device, HTTPS deployment, or DEVICE_VERIFIED status follows from these fixtures.

WebClient bounded decoding, explicit status handling and connection resource behavior were checked against [Spring's exchange documentation](https://docs.spring.io/spring-framework/reference/web/webflux-webclient/client-exchange.html) and [client configuration documentation](https://docs.spring.io/spring-framework/reference/web/webflux-webclient/client-builder.html), accessed 2026-09-12. The live documentation is currently 7.0.9; implementation compilation uses this repository's existing Spring Boot 3.3.4 dependency graph, with no version upgrade. Fresh transport tests, not the documentation version, establish the observed local behavior.
