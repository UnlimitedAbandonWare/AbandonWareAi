# 실제 사용자 시나리오

## 실행 전 고정할 것

현재 화면에서 기능·버튼·입력·상태를 확인하고 아래 사례를 실제 요소에 매핑한다. 입력은 무해한 합성 데이터만 사용한다. 각 사례에 `caseId`, 초기 상태, 입력 ID/의미 조건, 조작, 대기 상한, 기대 요청 수, 기대 화면, 정리 방법을 정한다. 없는 기능은 근거와 함께 `not_applicable`로 명시하고 필수 사례를 실패 후 분모에서 빼지 않는다.

기본 정상 입력 예시는 계산 검증이 쉬운 “2 더하기 2의 답을 숫자 한 개로만 알려줘”다. 원문을 증거로 저장하는 대신 synthetic case ID와 `answerMatchesExpected=true|false`를 기록한다. RAG 사용을 확인해야 하면 현재 접근 가능한 무해한 문서/출처에 대한 별도 질문과 확인할 사실을 먼저 고른다. 일반 산수 응답으로 검색·citation 정확성을 증명하지 않는다.

현재 계약의 client timeout은 90초, 요청 budget header는 80,000ms다. 실행 전 `display-core.js`에서 재확인하며, 짧은 관측 대기를 timeout이라고 보고하지 않는다. 개별 도구 대기는 60초 이하로 나누고 실제 deadline을 유지한다. 같은 논리적 입력을 무작정 반복하지 않는다.

| ID | 실제 조작 | 합격 관측 / 요청 경계 |
|---|---|---|
| M01 정상 왕복 | 질문 입력 → 전송 버튼 → 로딩 → 답변 → 다음/이전 카드 → 출처 화면 → 돌아가기 | 명시적 submit 1회에 sync 1개, 로딩 종료, 의미 조건을 만족하는 답변, 누락 없는 카드, 출처 유무를 정직하게 표시, focus 회복. fallback은 정상 답변 성공에 포함하지 않음 |
| M02 연속 질문 | M01 완료 후 다른 질문을 입력·전송 | 새 요청 1개, 같은 브라우저의 서버 session 연속성, 이전 답변이 새 답변으로 오인되지 않음. cookie 값을 읽지 않고 기존 서버 증거의 session hash/동일성만 기록 |
| M03 빈 입력 | 빈 값, 공백만 입력 후 버튼/Enter 시도 | 각각 sync 0개, 입력 안내 또는 비활성 버튼, 오류/로딩 고착 없음. 직접 API의 400만으로 UI validation을 통과시키지 않음 |
| M04 빠른 조작 | 정상 submit 직후 버튼 연타와 Enter, 로딩 중 다른 입력 시도 | 요청 1개 유지, UI 상태가 일관되고 stale 응답이 새 상태를 덮지 않음. IME 조합 중 Enter와 실제 확정/전송을 별도 확인 |
| M05 새로고침 | 유휴 상태 새로고침, 별도 사례에서 요청 중 새로고침 | shell 재진입과 입력 가능, 과거 질문 자동 재전송 0개, 유령 로딩 없음. 현재 제품의 세션 보존/초기화 정책과 비교하고 없는 저장 기능을 가정하지 않음. 서버 완료가 미확인인 작업은 해결 전 재전송하지 않음 |
| M06 지연·취소 | 지연을 관측/안전 주입 → Escape/취소, 별도 사례에서 client timeout까지 대기 → 같은 질문 Enter | 안내·로딩 해제·입력/focus 회복, `outcome-unknown`에서는 추가 호출 0개. abort는 서버 취소 증명이 아니며 90초 이후 늦은 답변이 현재 화면을 덮지 않아야 함 |
| M07 API 실패 | 400/413, 403, 409/422, 429, 503, 비JSON 응답/연결 실패를 독립 사례로 관측/안전 주입 | 상태별 안전한 안내, raw body 노출 없음, 로딩 종료. 429의 Retry-After를 존중하고 403/409/422/불명 결과를 새 키로 우회하지 않음 |
| M08 서버 재시작 | 소유권 입증된 task-owned 서버만 기존 실행기로 1회 재시작 → 같은 페이지에서 상태 확인 | 끊김/실패를 명시하고 끝없이 로딩하지 않음. 실제 서버 준비 뒤 새로운 명시적 질문의 정상 왕복. 기존 불명 작업 자동 재전송 0개 |
| M09 연결 복구 | task tab에만 일시 네트워크 차단/해제 가능 시 수행 → 재접속 → 명시적 새 질문 | 연결 오류 후 UI 회복, 중복 요청/이벤트 핸들러 없음, 새로운 정상 왕복. M08의 서버 재시작과 별도로 기록 |
| M10 화면·조작 | 일반 창과 실제 Display 크기에서 긴 답변/출처 카드, 방향키·Enter·Escape, 확대/축소/scroll 점검 | 가려진 전송/뒤로 버튼 없음, 읽을 수 있는 본문, 잘린 내용은 페이징으로 접근 가능, focus 표시·이동, 입력 도중 방향키가 카드 이동을 일으키지 않음 |

선택한 표면이 `receiver.html`인 경우 실제 화면에서 제공되는 연결·수신·재연결 동선을 매핑하고 송신 입력은 기존 소유 표면에서 수행한다. receiver에 없는 질문 입력 기능을 새로 만들지 않는다. 관련 `scripts/display_receiver_rag_contract_tests.cjs`는 supporting evidence다. 이번 범위와 무관한 음성/STT/TTS·계정·기기 작업은 제외한다.

## 안전한 실패 재현

실제 발생 오류를 먼저 사용한다. 도구가 지원하는 task tab 전용 interception/offline/throttling 또는 기존 전용 fixture로 재현할 수 있으면 목적·영향·해제 방법을 먼저 기록한다. 브라우저 API가 해당 기능을 제공하는지 현재 문서로 확인한다. 노출되지 않은 `route`, network, `evaluate` 기능을 추측해 호출하지 않는다.

주입/fixture 결과에는 `evidenceKind=browser-injected|client-fixture`를 붙인다. UI 오류 처리는 입증할 수 있지만 실제 백엔드/LLM 장애 처리나 정상 생성 증거로 승격하지 않는다. HTTP 응답이 실제로 발생하지 않은 offline 실패는 `httpStatus=null`이다. 503 fixture를 실제 admission 실패 원인이라고 보고하지 않는다.

각 사례의 `finally`에서 등록한 interceptor/지연/offline만 해제한다. 공유 네트워크·방화벽·DB·admission/security/provider 설정을 바꾸지 않는다. 다른 작업 소유 서버나 GPU 프로세스는 종료하지 않는다. 주입이 불가능하거나 실행 소유권이 없으면 해당 사례만 `evidence_needed`와 한 가지 다음 확인을 기록한다.

복구 뒤 실제 비주입 M01을 다시 수행한다. 오류 안내가 보인다는 사실만으로 재접속 복구를 통과시키지 않는다. 정상 왕복의 합격에는 전달뿐 아니라 동일 입력의 의미 조건과 Display 출력이 필요하다.

## 패치 후 재검증

최소 회귀 묶음은 `수정 전 실패 사례 + M01 + 영향받는 인접 사례`다. 전송/취소 변경이면 M03–M06, 연결 변경이면 M02/M05/M08/M09, 화면 변경이면 M10을 포함한다. 전체 필수 목록은 남겨두고 미실행을 숨기지 않는다.

실제 client 코드를 사용하는 기존 집중 명령:

```powershell
node --test .\scripts\meta_display_webapp_contract_tests.cjs
```

backend 변경은 기존 source contract에서 관련 Gradle 테스트와 격리된 build/cache를 선택한다. Node 통과, launcher 준비 검사, HTML GET200은 각각의 표면만 증명한다. 재시작/새로고침 뒤 현재 served asset와 패치 postimage/실행 산출물의 계보가 확인되어야 수정의 브라우저 효과를 주장한다.
