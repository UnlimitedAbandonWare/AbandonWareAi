# 보이지 않는 메커니즘을 조사하는 원리

눈에 드러난 결과는 내부 실행의 일부만 보여준다. 같은 화면이나 같은 로그 개수는 서로 다른 내부 경로에서 나올 수 있다. 기술적 통찰은 그 결과를 만드는 데 필요한 상태와 경계를 가설로 세운 다음, 경쟁 설명이 서로 다른 결과를 예측하는 지점을 찾는 데서 생긴다. 아래 연구는 이 조사 방법의 근거다. 특정인의 능력이나 제품에 관한 회고담을 검증한 자료는 아니다.

## 결과에서 책임 경계로 거슬러 올라가기

동적 프로그램 슬라이싱은 특정 실행에서 관심 있는 값에 영향을 준 문장을 데이터·제어 의존 관계로 좁힌다. 따라서 조사 출발점은 막연한 제품명보다 **관찰값, 실행 지점, 입력·설정, 실행 식별자**다. [Agrawal·Horgan, Dynamic Program Slicing, PLDI 1990](https://www.cs.columbia.edu/~junfeng/08fa-e6998/sched/readings/slicing.pdf)

스킬에는 이 원리를 수동 경계 추적으로 적용한다. 중복 효과가 관찰되면 결과 → 실제 송신 → 시도 → 콜백 → 등록·설정 순으로 책임 경계를 좁힌다. 메시지 큐, 비동기 콜백, 다른 프로세스로 넘어가는 연결에는 별도의 상관관계 증거가 필요하다. 호출 순서만으로 데이터 의존이나 원인을 확정하지 않는다.

한 실행에서 관찰한 경로는 실행되지 않은 다른 분기의 부재를 증명하지 못한다. “왜 실행했는가”와 함께 “어느 조건 때문에 실행하지 않았는가”를 조사해야 한다. 이 문서의 수동 추적은 정식 슬라이싱 도구의 실행 결과가 아니다.

## 정상·비정상의 차이를 줄이기

델타 디버깅은 같은 실패를 유지하는 입력이나 성공·실패 사이의 차이를 체계적으로 줄인다. 작은 재현 조건을 얻으면 어떤 차이가 판정을 바꾸는지 확인하기 쉽다. [Zeller·Hildebrandt, Simplifying and Isolating Failure-Inducing Input, IEEE TSE 28(2), 2002](https://www.st.cs.uni-saarland.de/papers/tse2002/)

적용 전에 판정기를 `PASS / 동일한 FAIL / UNRESOLVED`로 정의한다. 연결 실패나 테스트 환경 파손을 원래 버그의 재현으로 계산하지 않는다. 입력 조각, 플래그, 이벤트 순서를 줄일 수 있지만 현재 허용된 실험 표면 안에서만 수행한다. 시간·횟수 상한과 상태 복원이 먼저 정해져야 한다.

`ddmin`에서 말하는 1-minimal은 선택한 단위 하나를 더 제거하면 같은 실패가 유지되지 않는다는 뜻이며 전역 최소를 보장하지 않는다. 줄어든 재현 조건 자체가 버그의 의미나 개발자의 목적을 설명하지도 않는다. 비결정적 실패는 판정의 안정성을 따로 확인한다. [Zeller, The Debugging Book — Delta Debugging](https://www.debuggingbook.org/html/DeltaDebugger.html)

## 함께 나타난 것과 결과를 바꾼 것을 구별하기

관찰 자료의 연관성과 외부 개입의 효과는 다른 주장이다. 관찰 자료에서 인과 효과를 식별하려면 인과 구조에 관한 가정이 필요하다. 따라서 같은 결과를 만드는 가설이 여럿 남으면, 현재 관찰 범위에서 아직 구별되지 않는다고 기록한다. [Pearl, A Causal Calculus for Statistical Research, 1995; PMLR 재발행 2022](https://proceedings.mlr.press/r0/pearl95a.html)

프로그램에서도 성공·실패 실행의 상태 차이를 좁히고, 특정 상태 차이가 결과를 바꾸는지 관찰하는 방법이 연구되었다. [Zeller, Isolating Cause-Effect Chains from Computer Programs, FSE 2002](https://www.st.cs.uni-saarland.de/papers/fse2002/)

CPDA는 수정한 프로그램을 실행해 한 요소의 변화가 다른 요소의 행동에 영향을 주는 관찰을 수집한다. 이 연구는 프로그램 관계를 인과적으로 조사하는 접근을 뒷받침하지만, 단순히 파일을 읽거나 로그 두 줄을 비교한 것을 같은 실험이라고 부를 근거는 아니다. [Lee·Binkley·Feldt·Gold·Yoo, Causal Program Dependence Analysis, 2021, 원 논문 초록](https://arxiv.org/abs/2104.09107)

스킬에 적용할 때는 각 검사에 고정 조건, 변경 변수, 가설별 예상, 실제 결과, 잔여 혼란 요인을 적는다. 가설들이 똑같이 예측하는 화면을 다시 보는 대신 예측이 갈리는 경계를 관찰한다. 이러한 유한한 관찰의 한계는 모든 입력에 대한 프로그램 동치를 증명한 것과 다르다.

## 숨은 기능에는 존재·포함·등록·시간이라는 별도 조건이 있다

파일 존재와 배포 산출물 포함은 다르다. Gradle의 Java 플러그인은 sourceSet, 컴파일, 리소스, 클래스패스를 구분하며 프로젝트는 기본 구조를 바꿀 수 있다. 실제 저장소의 빌드 정의와 실행 산출물이 일반 문서의 기본 경로보다 우선한다. [Gradle, The Java Plugin](https://docs.gradle.org/current/userguide/java_plugin.html)

Lua는 호스트 프로그램에 내장될 수 있고, 호스트는 Lua가 호출할 C 함수를 등록할 수 있다. 따라서 Lua 문자열이나 함수 이름을 발견했을 때 확인할 경로는 호스트 바인딩 → 등록 → 로더 → 조건 → 호출 → 효과다. 문자열만으로 커널 드라이버에서 실행된다고 단정할 수 없다. [Lua 5.4 Reference Manual, §1](https://www.lua.org/manual/5.4/manual.html#1)

예를 들어 시작할 때 한 번만 `license && vmReady && sessionArmed`를 검사하는 구현이라면, 시작 후 세 값을 참으로 만들어도 등록을 다시 하지 않을 수 있다. 반대로 이미 등록한 기능을 이후 플래그 변경이 취소하는지도 별도 경로의 문제다. 이는 특정 제품의 역사적 사실이 아니라 조건 평가와 상태 유지 원리를 보여주는 **합성 사례**다. 실제 판정에는 평가 시점 값, 등록 기록, 재평가·해제 경로가 필요하다.

“기능은 왜 공개하지 않았는가”는 추가 질문이다. 의존성 부족이나 실패 테스트는 기술적 제약의 증거가 될 수 있지만, 출시 결정의 이유는 버전이 맞는 결정 기록이나 책임자의 설명이 있어야 확인할 수 있다. 라이선스 분기는 조건을 증명하며 비공개 동기를 자동 증명하지 않는다.

## 네트워크와 가상화 사례에 적용하기

Netty와 Apache MINA는 각각 공식 프로젝트 문서가 있는 네트워크 프레임워크다. JDK 자체에는 `SocketChannel` 같은 네트워크 API도 있다. 이들은 식별자를 확인해 구별해야 한다. “미나코”라는 기억 속 이름을 Apache MINA로 자동 치환할 근거는 없다. [Netty](https://netty.io/), [Apache MINA](https://mina.apache.org/mina-project/index.html), [JDK 17 SocketChannel](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/channels/SocketChannel.html)

중복 동작 조사의 유용한 관찰 단위는 사용자 동작 → 논리 요청 → 시도 → 호출 주체 → 송신 → 원격 효과다. 패킷 수, 쓰기 호출 수, 업무 처리 수는 서로 다른 단위다. 어떤 단위가 증가했는지 먼저 확인해야 라이브러리 결함, 재시도, 중복 등록, 관측 중복을 구별할 수 있다. 이 계보는 위 방법을 적용한 조사 설계이며 특정 중복 송신 버그의 증거가 아니다.

가상화의 경우 물리 CPU 기능, 호스트 하이퍼바이저, 게스트, 실제 선택된 실행 백엔드, 관찰 프로세스를 나눈다. 화면이 비슷하거나 기능 비트가 있다는 것만으로 같은 실행 경로를 사용한다고 결론내리지 않는다. VMware·BlueStacks의 특정 과거 버전 관계나 “시스템즈 6.5/6.7”의 정체는 이 자료로 확인되지 않는다. 정확한 제품·빌드가 확보될 때 해당 버전의 공식 문서와 런타임 기록을 조사한다.

## 적용 범위와 읽기 수준

자료 확인 기준일은 2026-09-10이다. 연구 결과를 현대 제품의 성능 수치나 스킬의 향상률로 전용하지 않는다. SciSpace 검색 초록은 원문을 찾는 단서이며, 중복 DOI나 저장소의 다른 버전은 독립된 재현 증거가 아니다. CPDA는 원 논문 초록 수준에서 사용했다. 문서의 가설·실험 양식은 연구 원리를 이 스킬에 적용한 설계 제안이다.

이 스킬이 하는 일은 관찰과 예측을 외부에서 검증할 수 있는 형태로 만드는 것이다. 제공되지 않은 다른 사용자의 대화, 모델의 비공개 내부 상태, 개인의 마음을 읽는 능력을 부여하지 않는다. 합성 사례의 성공은 실제 사건에서의 보편적인 정확도나 향상을 입증하지 않는다.
