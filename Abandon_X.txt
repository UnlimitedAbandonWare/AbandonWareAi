0. 요약 (Executive Summary)
--------------------------------------------------------------------------------
UAW.txt는 두 개의 서로 다른 문서가 한 파일에 붙어 있는 형태다.

  [전반부] 2026-07-26 정적 오버레이 감사 + do00~do11 패치 지시서
  [후반부] 포트폴리오 기능 설명 — 같은 기능들이 정상 작동하는 것처럼 서술

현재 소스와 대조한 결과:

  - 지시서의 결함 목록 중 상당수는 **이미 수리되었거나 상황이 바뀌어 stale** 하다.
    (예: AutoConfiguration.imports 누락 → 현재 등록됨)
  - 일부 핵심 결함은 **여전히 유효하고 오히려 악화** 되었다.
    (예: RuleBreak 미등록 — 구현 계보가 2개에서 8개로 증가)
  - 포트폴리오 서술은 **컴파일된 소스의 존재를 실행 증거로 오인** 하는 경향이 있다.
    canonical 스캔 경계 밖의 dormant 코드가 매우 많다.
  - 반대로 포트폴리오가 언급한 일부 기능은 **다른 이름으로 canonical 패키지에
    실구현** 되어 있다(예: com.example.lms.uaw.autolearn.*). 문서의 클래스명만
    오래된 것이다.

가장 중요한 실충돌 3건(P0):
  1. RuleBreak: 소비자는 존재하나 생산자가 서블릿 체인에 등록되지 않아 기능 전체가
     end-to-end로 사망. 구현 8개 중 살아있는 경로 0개.
  2. application.properties vs application.yml 이중 선언: properties가 우선하므로
     OCR은 yml 기본값(false/0.65)과 반대로 실질 true/0.78로 동작 — 운영 오독 위험.
  3. 진입점 이원화: canonical은 LmsApplication인데 AgentApplication이 계속 존재.
     잘못된 런처로 기동하면 스캔 경계가 달라져 다른 빈 그래프가 생성된다.

1. 교정된 런타임 경계 (UAW의 경로 가정을 수정)
--------------------------------------------------------------------------------
UAW 전반부는 src/main/java, src/main/resources 류의 표준 레이아웃을 가정했다.
현재 실제 구조는 build.gradle.kts가 정의한 커스텀 sourceSet이다.

  canonical 부팅 모듈:
    - 소스     : main/java
    - 리소스   : main/resources
    - 테스트   : src/test/java (+ chatUiTest, gatewaySecurityTest,
                 crossSubsystemContractTest 등 별도 sourceSet)
    - 부트클래스: com.example.lms.LmsApplication   ← build.gradle.kts mainClass
                  스캔 = com.example.lms + com.nova.protocol

  보조 모듈 (:app):
    - 소스     : app/src/main/java_clean
    - 리소스   : app/src/main/resources
    - imports  : AddonsAutoConfiguration, NovaProtocolConfig

  비활성/참조 루트(문서상): project/src, app/src/main/java, demo-1, lms-core,
    백업/아카이브/bin 산출물 — 이 문서의 판정 대상에서 제외.

스캔 경계의 실효 (중요):
  canonical 스캔 = com.example.lms + com.nova.protocol.
  따라서 아래 패키지들은 "컴파일은 되지만 빈으로 올라가지 않는" dormant 상태다:
    com.abandonware.ai.*, com.abandonwareai.*, com.abandonware.patch.*,
    루트 패키지들(config/, web/, service/, strategy/, trace/, guard/)

  단, ai.abandonware.nova.* 도 스캔 밖이지만
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  에 등록된 6개 autoconfig가 @Bean 메서드로 명시 생성 → 도달 가능:
    NovaOrchestrationAutoConfiguration (~67 @Bean)
    NovaFailurePatternAutoConfiguration (~10 @Bean)
    NovaZero100AutoConfiguration (3 @Bean)
    NovaOpsStabilizationAutoConfiguration (~11 @Bean)
    NovaDebugPortAutoConfiguration (3 @Bean)
    AgentDbContextAutoConfiguration

웹 스택 판정:
  build.gradle.kts에 spring-boot-starter-web + spring-boot-starter-webflux가
  동시에 있으므로 Spring Boot는 서블릿 모드로 부팅한다. 즉
  org.springframework.web.server.WebFilter 구현체는 서블릿 체인에 적용되지
  않는다(빈으로만 존재). §3-B 참조.

3. 잔여 실충돌 상세 (우선순위)
--------------------------------------------------------------------------------

P0-A. RuleBreak — 기능은 있는데 아무 경로도 살아있지 않다
    소비자: RetrievalOrderService.planDslOrder()가
    RuleBreakContextHolder.get()를 읽어 SPEED_FIRST 정책이면
    VECTOR_KG_WEB 순서로 전환한다(com.example.lms.strategy, canonical, live).
    생산자 후보 8개와 실효:
      1) com.example.lms.guard.rulebreak.RuleBreakInterceptor — canonical,
         evaluator 경유(안전), ContextHolder set/clear 구현. 미등록.
      2) com.example.lms.nova.RuleBreakInterceptor(novaRuleBreakInterceptor)
         — 빈 존재, NovaRequestContext에 씀. 미등록 + NovaRequestContext의
         getRuleBreak/hasRuleBreak를 호출하는 소비자가 코드상 없음(write-only).
      3) com.nova.protocol.filter.RuleBreakInterceptor — WebFilter.
         서블릿 모드 부팅에서 적용 불가 + RuleBreakContext.KEY를 읽는
         리액티브 소비자 없음(write-only) + NovaProperties.rulebreakEnabled
         기본 false.
      4) com.abandonware.patch.plan.RuleBreakInterceptor —
         PatchAutoConfiguration이 addInterceptor로 등록하나 해당 패키지는
         스캔 밖이고 imports에도 없음 → dormant.
      5) com.abandonware.ai.agent.integrations.web.RuleBreakInterceptor —
         스캔 밖 dormant.
      6) com.abandonwareai.nova.RuleBreakInterceptor — 스캔 밖 dormant.
      7) com.abandonwareai.zerobreak.interceptor.RuleBreakInterceptor —
         UAW가 경고한 nonblank-승인 계보. 스캔 밖 dormant. 활성화 금지 유지.
      8) web.RuleBreakInterceptor(루트 패키지) — dormant.
    결과: 요청 경로 어디에서도 RuleBreakContextHolder가 채워지지 않으므로
    planDslOrder()의 rulebreak 분기는 영구 null → 기능 정의와 실제 실행의
    최대 모순. UAW의 "미등록" 판정은 맞지만 "구현 2개"라는 집계는 현재 8개로
    교정 필요.

P0-B. 설정 우선순위 함정 — properties가 yml을 무력화
    §2-E 참조. OCR 의도(false vs true)를 문서만 보고 판단하면 실제 동작과
    반대 결론이 나온다. 정리 전에 property-origin/Environment 확인이 선행.

P0-C. 진입점 이원화
    canonical = LmsApplication(com.example.lms + com.nova.protocol).
    AgentApplication(com.abandonware.ai.agent + com.example.lms) 존재 지속.
    두 런처는 스캔 범위가 달라 서로 다른 빈 그래프를 만든다. UAW의 충돌
    목록이 성립하던 환경이 바로 이 대체 런처다. 삭제는 별도 승인 사안이나,
    "어느 것이 진짜인가"는 문서상 명시되어야 한다.

P1-D. Plan DSL의 이분화(§2-D) — 문서가 양극단으로 틀림.
P1-E. plans/ 별칭 중복(§2-H) — 로더가 *.yaml과 *.v1.yaml을 어떻게 고르는지
      미확인. 중복 키가 있으면 의도와 다른 플랜 선택 가능성.
P1-F. write-only 컨텍스트 — NovaRequestContext(ruleBreak)와
      com.nova.protocol RuleBreakContext.KEY는 쓰는 코드만 있고 읽는 코드가
      없다. "미래용"이면 표시, 아니면 dead code.

P2-G. dormant 중복 계보 확대 — UAW는 "단순 클래스명 중복 144개"로 기술했으나
      현재는 같은 의미의 구현이 계보로 복제된 상태:
        RuleBreakInterceptor ×8, PIISanitizer/PiiSanitizer ×7,
        ScoreCalibrator ×6, FinalSigmoidGate ×5, CitationGate ×4+,
        PlanDslLoader ×3, TraceFilter ×3, DomainWhitelist ×3,
        KnowledgeGraphHandler ×3, DppDiversityReranker ×3, SelfAskPlanner ×3,
        OverdriveGuard ×3, ExtremeZSystemHandler ×2, WebInfraConfig ×2,
        RetrievalOrderService ×2(모듈 간), VirtualPointService ×2,
        MatrixTelemetryExtractor ×2, RawMatrixBuffer/RawSlotExtractor ×3 …
      canonical 부팅에는 피해가 없으나, 향후 스캔 확장·리팩터링 시
      어떤 것이 정본인지 판별 불가 → 정리 대상(삭제 전 unused 증명 필수).

4. 포트폴리오 기능 주장 vs 실제 배선 매트릭스
--------------------------------------------------------------------------------
분류: LIVE=canonical 도달 경로 존재 / PARTIAL=일부만 / DORMANT=컴파일되나
스캔 밖 / DISABLED=구현 있으나 기본 off / ABSENT=해당 이름의 클래스 부재 /
META=선언만 있고 실행기 없음.

  기능(포트폴리오 명칭)          판정    근거
  --------------------------- ------- --------------------------------------
  Failure Pattern 분석         LIVE    NovaFailurePatternAutoConfiguration
                                       (imports 등록, ~10 @Bean)
  Zero-100                     LIVE    NovaZero100AutoConfiguration +

5. 안전 해소 순서 (기능 유지 전제 — 한 번에 한 근본 원인)
--------------------------------------------------------------------------------
순서는 "행동하면서 기존 기능을 깨지 않는" 기준. 각 항목은 독립 커밋 단위.

  1) [P0] RuleBreak 생산자 등록 — canonical만:
     WebMvcConfig.addInterceptors에
     com.example.lms.guard.rulebreak.RuleBreakInterceptor를 등록.
     evaluator는 admin-token 일치 방식이므로 토큰 미설정 시 자동 비활성 →
     안전. 절대 zerobreak 계보/nova-protocol reactive 필터로 대체 금지.
     등록 후 planDslOrder() SPEED_FIRST 분기가 처음으로 실제 도달 가능해지므로
     해당 분기의 동작을 계약 테스트로 추가할 것.
     (대안: 기능을 쓰지 않기로 결정하면 소비자 측 dead 분기를 정리하고 문서에
     비활성 명시 — 등록과 정리 중 하나를 선택, 방치가 최악.)

  2) [P0] 설정 이중 선언 해소:
     ocr.enabled / ocr.min-confidence / local-llm.base-url /
     retrieval.vector.enabled 를 한 포맷으로 단일화. 어느 쪽이 정본인지
     결정하기 전에 property-origin 확인(Environment 또는 부팅 로그).
     OCR 의도값(true vs false)을 먼저 확정 — 현재는 properties가 yml을 무력화.

  3) [P1] 런처 단일화 명시:
     LmsApplication이 canonical임을 문서/주석으로 고정. AgentApplication은
     레거시 대체 런처로 표시(삭제는 별도 승인). 부팅 스크립트가 항상
     mainClass를 거치는지 확인.

  4) [P1] Plan DSL 계약 문서화:
     planDsl.status=not_used는 "broad executor 미배선"이라는 의도된 계약.
     소비되는 키(hint/projection/plan order)만 문서에 명시하고,
     planDslOrder()는 이름 오인 가능성을 주석으로 처리.

  5) [P1] plans/ 별칭 정리:
     brave.yaml vs brave.v1.yaml 등 비-v1 사본이 로더 선택 규칙과 충돌하는지
     확인 후 단일화.

  6) [P2] dormant 계보 격리:
     스캔 밖 중복은 즉시 위험이 아니므로 삭제보다 compile exclude 또는
     아카이브 이동이 안전. 각 후보에 대해 "스캔 밖 + 미import + 미호출"
     3중 증명 후 제거. zerobreak 계보는 "활성화 금지" 주석 유지.

  7) [P2] 정크/불일치 정리:
     test_mod.java, ChatService_old/copy shim, 패키지-경로 불일치 3건,
     루트 패키지 잔재 — 각각 별도 커밋.

  8) [문서] UAW.txt 갱신 규칙:
     이미 해소된 지시(do02 등)는 "RESOLVED" 표시, stale 판정은 본 문서의
     판정표로 대체. 포트폴리오 서술에는 §4의 LIVE/DORMANT/ABSENT 태그 병기
     권장.

유지해야 할 UAW 거버넌스 규칙(여전히 유효):
  - allow-bean-definition-overriding=true 금지
  - nonblank 토큰=승인 경로 금지
  - plan YAML은 실행기 증명 전까지 hint/metadata로 취급
  - 비밀값·환경변수명 출력 금지
  - 근본 원인 하나=커밋 하나, Observation→Patch→Setup→Verification 형식
  - 완료 주장에는 신선한 빌드/테스트 명령 + exit code 필요
