## L1 — failover 9fail 중 "실행 전 거절" 묶음 (FallbackAwareChatModel만)
1. `LlmRouterRuntimeDeviceFailoverTest`를 focused로 돌려 RED를 확정한다. 메서드마다 assertion 기대값과 실제값을 v2 F6의 묶음 A~E와 대조해 표로 만든다.
2. B(GPU is lost), C(invalid main_gpu / available devices: 0), D(vram_oom), E(HTTP 200 classified failure)는 provider가 생성을 시작하지 못한 실패다. 이 경우만 `sameRequestFallbackAllowed`(:473-480)에서 **명시적으로 구성된 다른 장치나 다음 클라우드로 정확히 1회** 허용하도록 최소 수정한다. 근거는 `LlmGatewayFailureClassifier.java:272-279` 분류다.
3. 반례 테스트를 추가한다: `TIMEOUT_SOFT` + `providerReceiptObserved=false`는 **계속 막힌다**. 중복 실행 방지 guard의 의도를 유지하는 것이다.
4. A묶음(non-GPU runtime failure, all-local-open → 다음 클라우드)은 guard 정책과 충돌할 수 있다. 근거가 약하면 수정하지 않고 ASK_ONCE #2로 올린다(선택지 2개 + 각 위험).

## L2 — 실제 선택 모델 미리 데우기 (LocalLlmProcessManager + PageController)
1. LocalLlmProcessManager에 `warmupChatModelAsync(String model)` 정도의 작은 메서드를 추가한다. 기존 `warmupOllama()` 경로와 keep-alive / timeout-ms 설정을 재사용한다.
   - 비동기로 돌고, 같은 모델은 진행 중 1건만 허용한다(중복 제거). 이미 로드됐으면(`/api/ps` 또는 기존 health 캐시) 건너뛴다.
   - `local-llm.warmup.enabled=false`이거나 GPU health / power-fallback 게이트가 막으면 아무것도 하지 않는다.
   - 실패는 로그와 상태값만 남기고 예외를 던지지 않는다.
2. PageController GET /chat에서 위 메서드를 **비동기로 한 줄** 호출한다. 페이지 응답을 기다리게 하면 안 된다.
3. 어떤 모델을 데울지는 서버에 이미 있는 "현재 선택/기본 채팅 모델" 조회 호출이 있으면 그걸 쓴다. 한 줄 조회로 해결되지 않으면 `llm.chat-model` 실효값을 쓰고, 사용자별 선택 반영은 HOLD_FOR_CODEX로 넘긴다.
4. 테스트: 중복 제거, 비활성 시 무동작, 이미 로드됐으면 건너뜀, 컨트롤러가 블로킹하지 않음. RED→GREEN으로 확인한다.
