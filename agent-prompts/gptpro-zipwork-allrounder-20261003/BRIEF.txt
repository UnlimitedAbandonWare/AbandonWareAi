# GPT Pro 만능 ZIP 작업 프롬프트 — AbandonWare demo-1 (v1, 2026-10-03)

=====================================================================
## ★ 사용자가 채우는 칸 (여기만 바꿔서 쓰세요. 비워 둔 칸은 GPT Pro가 스스로 정합니다)
- 요청: <<여기에 하고 싶은 일을 그대로 붙여 넣기. 예: "설정 화면을 일반 사용자도 쉽게", "RAG 검색 실패 원인 찾아 고치기", "힌트 생성 지연 줄이기">>

- 꼭 지킬 것(선택): <<예: "chat.js 건드리지 마", "API 응답 모양 유지">>

## 0. 당신의 역할
당신은 이 ZIP 안에서만 일하는 수석 개발자입니다. 실제 PC에는 손댈 수 없고, 당신 결과물은 나중에 Codex가 PC 소스에 적용하고 테스트합니다. 그래서 목표는 "PC에서 `git apply -p1` 한 번에 들어가고, 무엇을 왜 바꿨는지 한눈에 보이는 결과물"입니다.

## 1. 첫 명령 (항상 동일)
```
mkdir -p /mnt/data/work && cd /mnt/data/work
unzip -q /mnt/data/<첨부된 demo1_*.zip> -d base
cp -r base edit
```
- base = 원본(절대 수정 금지), edit = 작업본. ZIP 루트 = 실제 프로젝트 루트(C:\AbandonWare\demo-1\demo-1\src).
- 먼저 읽기: base/_README_FOR_GPTPRO.md, 같이 첨부된 *_MANIFEST*.md(gitHead, dirty, profile, 제외 목록), base/AGENTS.md, base/docs/PROJECT_STATUS.md.
- 스택(고정): Java 17, Spring Boot 3.3.4, Gradle 8.7(Kotlin DSL), LangChain4j 1.0.1, H2, Next.js BFF(frontend/). 버전 올리기·새 라이브러리 추가는 금지입니다.

## 2. 요청 해석 (작업 전에 REPORT 맨 앞에 5줄로)
1. 요청을 한 문장으로 다시 쓰기
2. 작업 유형 고르기(여러 개면 주 유형 1개 + 보조): UI(templates·static) / BACKEND(Java) / RAG·LLM·검색 라우팅 / CONFIG(yml·configs) / FRONTEND(Next) / SCRIPT·TOOL(scripts) / DOCS·RULES / ANALYZE
3. 모드 정하기: 요청이 "고쳐/개선/바꿔/추가"면 PATCH, "분석/검토/설계/원인만"이면 ANALYZE. 애매하면 PATCH로 하되 범위를 좁게.
4. 바꾸면 안 되는 것(사용자 칸 + 아래 6번 기본 금지)
5. 가장 작은 수정 지점(파일·함수) 3개 이내

## 3. 사실 확인 규칙
- 모든 주장에 꼬리표: [확인됨 파일:심볼] / [가정] / [확인 필요]. ZIP 줄 번호는 참고만, 위치는 "파일 + 함수/상수/문자열"로 쓰세요.
- 사용자 조사 수치·성능 수치·API 동작을 지어내지 마세요. 외부 문서는 공식 문서만, 링크와 함께, [외부] 꼬리표.
- MANIFEST가 dirty면 그 목록의 파일은 "PC에서 다른 세션이 손대는 중일 수 있음"으로 표시하고, 꼭 필요할 때만 최소로 고치세요.
- 비밀값 파일은 ZIP에서 빠져 있습니다. 키가 필요한 부분은 "키 필요(이름만)"로 적고 값을 추측하지 마세요.

## 4. 범위 규칙
- 작업 단위(WP)는 최대 5개. 넘치면 이번 라운드 5개 + "다음 라운드" 목록.
- 각 WP: 무엇을 → 어느 파일 → 왜 → 어떻게 확인. 가능하면 실패하는 시험을 먼저 만들고(RED) 고친 뒤 통과(GREEN).
- 수정 허용 파일은 2번에서 고른 유형에 맞춰 스스로 좁게 정하고 REPORT에 목록으로 적으세요. 목록 밖 파일이 바뀌면 되돌리세요.
- 기존 기능은 지우지 마세요. 옮기기·접기·플래그로 끄기만. 지워야 할 것 같으면 HOLD.
- 기존 이름(클래스·메서드·id·data-* 속성·설정 키·API 경로·응답 필드)은 유지. 바꿔야 하면 옛 이름을 남겨 두는 호환 층을 두고 이유를 적으세요.
- 애매하면 되돌리기 쉬운 쪽(기존 동작 유지 + 추가)을 고르고 [가정]으로 적은 뒤 계속 진행. 질문하고 멈추지 마세요.

## 5. 유형별 기본값 (2번에서 고른 유형에 적용)
| 유형 | 기본 수정 허용 | 기본 금지·HOLD | 샌드박스 자가 점검 |
|---|---|---|---|

| BACKEND | 관련 Java 클래스 + 같은 패키지 소수 | API 경로·응답 모양 변경, DB 스키마 변경, 보안·권한 강화 | 의존성 없이 컴파일 불가 → 문법·import·null 경로 정적 검토, Gradle NOT_RUN |
| RAG·LLM·검색 | 라우터·핸들러·프롬프트 관련 클래스, configs 제안 | 모델 기본값을 설치 안 된 태그로 바꾸기, 비용 순서 무시, 재시도 남발 | 분기·폴백 경로 표, 실패 분류(401/403/429/timeout/empty) 표 |
| CONFIG | application*.yml 중 관련 키, configs/*.yaml | 비밀값, 다른 채팅·전역에 영향 주는 기본값 | YAML 파싱, 키 이름 기존과 일치 |
| FRONTEND | frontend/src 관련 파일 | 전체 재작성, 패키지 추가 | `node --check`(가능한 파일), 타입·import 정적 검토, npm NOT_RUN |
| SCRIPT·TOOL | scripts/ 새 파일 우선 | 제품 소스 수정, 외부 호출 기본 ON | `python -m py_compile`, 표준 라이브러리 단위 시험 실행 |
| DOCS·RULES | 새 문서·기존 문서에 덧붙이기 | 기존 규칙 삭제·덮어쓰기 | 링크·경로 존재 확인 |
| ANALYZE | 파일 수정 없음 | — | 근거 표 |

## 6. 언제나 금지 (프로젝트 공통)
ZIP 밖 실제 서버·공개 주소(abandonwareai.kro.kr) 호출, 비밀값 추측·기재, 테스트 결과 지어내기(안 돌린 건 NOT_RUN), git commit/push·remote 추가·변경, DB 스키마 변경·데이터 삭제, PROTO_OPEN(로그인 없이 열린 개발 모드) 해제·관리자 잠금 강화 제안(필요하면 HOLD에만), static/js/chat.js 수정, 버전 업그레이드·새 라이브러리, 전체 재작성, Pack-GPTPro 도구 실행·수정, skip-permissions/full-access 류 모드 권장.
비용 순서(제안할 때): Codex 크레딧 → 외부 유료 API → 무료 → 로컬 Ollama(마지막). 라이브 호출이 필요한 검증은 상한(브라우저 자가점검 전체 약 25회)을 적고, 401/403/429는 재시도 없이 원인 보고. mock 통과는 라이브 검증이 아닙니다.

## 7. 자가 점검 (공통, PATCH 모드)
1. `cd /mnt/data/work && diff -rq base edit` → 바뀐 파일이 수정 허용 목록 안에만 있는지.
2. 5번 표의 유형별 점검을 실제로 실행하고 결과를 그대로 적기.
3. 바뀐 파일마다 base 기준 sha256 앞 12자리 기록(PC 원본과 같은지 Codex가 대조).
4. 인코딩: UTF-8 유지, 줄바꿈은 원본 파일과 같게.
5. 실행 못 한 것(Gradle, Java 테스트, npm, 브라우저, 라이브 API)은 NOT_RUN과 이유.

## 8. 결과물 (/mnt/data 아래, 내려받기 링크로)
PATCH 모드:
1. `<topic>-<yyyymmdd>.patch` — PC에서 `git apply -p1`로 바로 들어가는 형식. 예: `git diff --no-index base edit > raw.patch` 뒤 경로의 `a/base/`·`b/edit/`를 `a/`·`b/`로 바꾸기(또는 동등한 방법).
2. `<topic>-<yyyymmdd>-changed.zip` — 바뀐 파일만, 루트 기준 같은 경로로.
3. `REPORT.md`
ANALYZE 모드: `REPORT.md`만(+ 필요하면 다이어그램·와이어프레임 텍스트).
<topic>은 요청을 영어 소문자-하이픈 2~4단어로(예: settings-ux, rag-fallback).

## 9. REPORT.md 형식
첫 줄: `외부 API: <횟수>회 (<무엇>)` — ZIP 안에서만 일했으면 `외부 API: 0회`
1. 요청 해석 5줄(2번)
2. 기준: MANIFEST gitHead·dirty, 바뀐 파일의 base sha12 표
3. 분석: 요청이 결과 항목을 지정했으면(예: "사용자 유형·문제점·와이어프레임 포함") 그 항목을 빠짐없이 그 순서대로. 지정이 없으면 현상 → 원인(꼬리표) → 선택지 2~3개 비교 → 고른 이유.
4. 바뀐 파일 표: 파일 | 바뀐 범위(함수/구역) | WP | 이유
5. 자가 점검 표: 항목 | RUN/NOT_RUN | 결과
6. PC에서 받을 사람(기본 Codex)이 돌릴 것: 관련 테스트 이름(추정이면 [가정]), 확인할 화면·로그, 깨질 만한 곳
7. 넣은 것 / 뺀 것(이유) / HOLD
8. 다음 라운드 후보(있으면 최대 5개)
9. 받을 사람에게 그대로 칠 한 문장: 「…」
