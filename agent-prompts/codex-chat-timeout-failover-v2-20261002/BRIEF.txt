   - A묶음(non-GPU runtime failure, all-local-open)은 테스트가 기대하는 정책과 guard가 충돌하는지 판정한다. 테스트 기대가 옳다는 근거가 약하면 **테스트를 약화하지 말고** ASK_ONCE #2로 올리고, 나머지 묶음은 계속 진행한다.
3. `sameRequestFallbackAllowed` 허용 조건과 wrap 집합을 최소 범위로 고친다. 근거가 되는 classifier는 `LlmGatewayFailureClassifier.java:272-279`다.
4. 반례 테스트를 1개 이상 추가한다: TIMEOUT_SOFT이고 `providerReceiptObserved=false`인 모호한 실패는 **계속 막혀야** 한다.

## WP2 — 콜드 로드 timeout 근본 수정 (주 작업)
아래 순서대로 Self-Ask로 고른다. 기본 방향은 (a)+(b)이고 (c)는 선택이다.
- (a) **실제로 고른 모델을 미리 데운다.**
  - 기존 `LocalLlmProcessManager` 워밍업 메커니즘을 재사용한다. 고정된 기동 모델 하나가 아니라 **요청이나 설정에서 실제로 선택된 로컬 모델**을 데운다.
  - 트리거: /chat 페이지 서버 렌더(`PageController` GET /chat) 또는 모델 선택이 확정되는 서버 지점. 비동기, 중복 제거(같은 모델은 진행 중 1건만), 실패해도 조용히 넘어가며 GPU health/power-fallback 게이트를 따른다.
  - keep-alive는 기존 설정 키를 쓴다. 새 키가 필요하면 기본값을 현재 동작과 같게 둔다. 신규 키는 additive로 최대 3줄이다.
  - **chat.js는 수정하지 않는다.**
- (b) **로드 단계를 별도로 다룬다.** 요청 시점에 모델이 아직 안 올라와 있고(`/api/ps` 기준, 또는 기존 health 캐시) `providerReceiptObserved=false`이면, 첫 토큰 대기를 12s로 자르지 않는다. 대신 **남은 요청 예산 안에서** 로드 완료까지 기다린다.
  - 예산이 정말 바닥나 끊길 때는 Ollama 로드를 취소하지 않는다. 로드가 백그라운드에서 끝나게 해서 **다음 요청은 따뜻한 상태**가 되게 한다. 로드-중단 악순환(F3)을 끊는 것이 핵심이다.
  - 실패 코드도 구분한다: 로드 중 예산이 바닥났으면 `model_loading_budget_exhausted` 같은 세부 reasonCode를 trace와 로그에 남긴다. SSE 표면 코드를 바꾸려면 chat.js 호환을 먼저 확인하고, 호환이 안 되면 그 부분만 HOLD한다.
- (c) 선택: 위 두 가지로도 30s 예산 안에 답이 안 나오면, 예산 상향이 아니라 "로드 중" 상태를 기존 SSE 이벤트 형식(chat.js가 이미 처리하는 이벤트)으로 알리는 방법만 검토한다. 새 이벤트 타입이 필요하면 HOLD한다.
- 금지: 전역 `llm.timeout-seconds`, 30s 요청 예산, `public.request-budget.*` 값을 단순히 올리는 것. 바꿔야 한다면 근거와 함께 HOLD한다.
- 테스트: (a) 중복 제거·비동기·게이트, (b) 콜드 상태에서 12s를 넘겨도 예산 안이면 성공하는 경우, 예산을 다 써도 로드를 취소하지 않는 경우, 웜 상태는 기존 12s 그대로인 경우. 각각 RED→GREEN이다.
